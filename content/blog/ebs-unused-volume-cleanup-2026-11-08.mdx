어느 날 동료가 MS Teams로 AWS 비용 최적화 알림을 공유해줬다. 서울 리전의 EBS에서 미사용 리소스가 25개 탐지되었고, 모두 줄이면 월 500달러 정도 아낄 수 있다는 내용이었다. 25개 모두 실행 중이 아닌 EC2에 붙어 있었지만, 실제로 안 쓰는 건지는 동료도 확신하지 못하여 공유만 해둔 상태였다. 그래서 일단 EC2 콘솔의 볼륨 목록부터 열어봤는데 이상했다. 36개 중 거의 전부가 `사용 중`으로 표시되어 있었다. 알림은 미사용인데 콘솔은 사용 중으로 표시되니 둘 중 하나는 틀린 셈이었다.
##### 사용 중의 정체, 연결됨

알고 보니 콘솔과 알림이 말하는 "사용 여부"의 기준이 서로 달랐다. EBS 콘솔의 `in-use`는 볼륨이 인스턴스에 **연결(attached)** 되어 있다는 뜻일 뿐 그 인스턴스가 켜져 있는지는 따지지 않는다. 반면 비용 최적화 알림의 "미사용"은 볼륨이 붙은 인스턴스가 **실행 중이 아니라는** 뜻이었다. 즉 꺼진 서버에 붙은 볼륨은 콘솔에서는 `사용 중`으로, 알림에서는 "미사용"으로 표시되었던 것이다. 

| 구분              | 기준               | 의미                 |
| --------------- | ---------------- | ------------------ |
| EBS 콘솔 `in-use` | 인스턴스에 연결되어 있는가   | 인스턴스가 꺼졌는지는 무관     |
| 비용 최적화 알림 "미사용" | 연결된 인스턴스가 실행 중인가 | 꺼진 서버에 붙은 볼륨 = 미사용 |

문제는 요금이었다. EC2를 중지하면 인스턴스 요금은 멈추지만, 붙어 있던 EBS 볼륨은 그대로 남아 프로비저닝한 용량 전체에 대해 요금이 계속 나간다. 그런데 더 이상 쓰지 않는 서버들이 제거되지 않은 채 중지 상태로 쌓여 있었고, 그 서버에 붙은 볼륨들이 조용히 돈을 쓰고 있었다. 인스턴스 목록을 보니 27대 중 17대가 `중지됨` 상태였다. 다만 잠시 꺼둔 서버와 오래전에 멈춘 채 방치된 서버가 섞여 있어서, 중지됨이라는 상태만으로는 지워도 되는 볼륨인지 알 수 없었다.
##### 볼륨 현황 한눈에 보기

콘솔에서는 볼륨, 인스턴스 상태, 중지일을 한 번에 볼 수 없어서 CloudShell에서 AWS CLI 결과를 합쳐 한 장으로 모았다. 중지일은 인스턴스의 `StateTransitionReason`에서 꺼냈고, 월 비용은 서울 리전 정가로 계산했다.

![ebs-unused-volume-cleanup-2026-11-08_1|722](/ebs-unused-volume-cleanup-2026-11-08/ebs-unused-volume-cleanup-2026-11-08_1.png)

상태별로 합산하면 이렇다.

| 인스턴스 상태 | 볼륨 수 | 용량        | 월 비용   |
| ------- | ---- | --------- | ------ |
| running | 11개  | 902 GiB   | 약 $95  |
| stopped | 23개  | 5,246 GiB | 약 $498 |
| 미연결     | 2개   | 80 GiB    | 약 $7   |

stopped 23개와 미연결 2개를 더하면 25개, 월 약 $505로 알림이 말한 개수와 금액에 맞았다. 이제 이 25개 중 무엇을 지워도 되는지만 가리면 되었다.

##### 어떤 서버의 볼륨을 지워도 괜찮을까

물론 서버가 중지됐다고 해서 당연스레 그 볼륨을 지워도 되는 건 아닐 것이다. 잠시 꺼둔 서버일 수도 있기 때문이다. 그래서 볼륨을 지울 기준이 필요했고, 나는 얼마나 오래 꺼져 있었는가를 기준 삼아 서버 17대를 세 그룹으로 나누기로 했다.

|그룹|서버 수|월 비용|처리|
|---|---|---|---|
|6개월 이상 중지|6대|$354|볼륨 정리|
|1~4개월 중지 (테스트·시뮬레이션)|7대|$84|볼륨 정리|
|최근 10일 이내 중지|4대|$60|유지|

6개월 이상 꺼져 있던 서버 6대의 디스크는 이랬다.

|디스크|중지일|월 비용|
|---|---|---|
|gp3 1,118GiB × 2|2025-10-14|$204|
|gp2 500GiB|2025-09-11|$57|
|gp2 350GiB|2026-01-08|$40|
|gp3 350GiB|2026-04-18|$32|
|gp3 200GiB|2025-08-11|$18|
|gp3 30GiB|2026-01-27|$3|

맨 위의 서버가 가장 크리티컬한데 t2.micro 인스턴스에 2.2TB 디스크가 붙어 있었고 이 서버 하나가 전체 비용의 40%였다. 1년 넘게 꺼져 있던 서버도 여럿이라, 이 그룹의 볼륨은 정리 대상으로 판단했다. 1~4개월 전에 멈춘 7대는 테스트나 시뮬레이션용으로 만든 환경이라 볼륨을 같이 정리하기로 했다.

반면 최근 10일 이내에 중지된 4대는 이번 달에 만든 환경이라 작업 중에 잠시 꺼둔 것일 가능성이 높아 보였다. 알림은 이 서버들도 "지금 꺼져 있다"는 이유만으로 미사용으로 분류했는데, 알림의 25개를 그대로 다 지웠다면 진행 중인 작업을 날렸을 것이다. 그래서 이 4대는 유지하기로 했다. 어디에도 붙어 있지 않던 볼륨 2개(월 $7)는 같은 날 서버를 다시 만들면서 남은 것으로 보였지만, 담당자 확인 후 처리하기로 하고 보류했다.

##### 어떻게 안전하게 지울까

앞서 나는 오래 꺼져 있던 서버의 볼륨을 지우는 쪽으로 기준을 세웠다. 다만 오래 꺼져 있었다고 해서 쓰지 않는다고 온전히 확신할 수는 없었다. 그래서 확신이 없는 부분은 되돌릴 수 있는 방법으로 메우기로 했다. 볼륨을 바로 삭제하지 않고, 스냅샷 백업 → 서버에서 분리 → 삭제 순으로 정리하기로 한 것이다.

스냅샷을 고른 건 복원 수단이면서 비용도 줄어서다. 볼륨은 데이터가 얼마나 찼든 프로비저닝한 용량 전체에 요금이 붙지만, 스냅샷은 실제로 쓴 블록만 증분으로 저장하고 단가도 더 싸다. 1,118GiB짜리 디스크라도 안에 든 데이터가 적으면 스냅샷은 훨씬 적게 나온다.

||EBS 볼륨 유지|스냅샷 (표준)|
|---|---|---|
|과금 기준|프로비저닝 용량 전체|실제 사용 블록만 (증분)|
|단가 (gp3 기준)|$0.0912/GB-월|$0.05/GB-월|

스냅샷에는 표준과 아카이브 계층이 있는데, 한 달만 관찰하고 지울 계획이라 표준을 골랐다. 아카이브는 보관 단가가 $0.0125/GB-월로 훨씬 싸지만 90일 최소 보관 기간이 있고, 복원하는 데 수 시간에서 수일이 걸린다. 관찰 기간에 복원 요청이 오면 바로 대응할 수 있어야 해서 즉시 복원되는 표준이 맞았다.

볼륨을 분리하는 단계와 삭제하는 단계를 나눈 것도 같은 이유였다. 분리는 되돌릴 수 있지만 삭제는 되돌릴 수 없다. 서버 자체도 삭제(terminate)하지 않고 껍데기(stopped)로 남기기로 했다. 볼륨이 없는 중지 서버는 비용이 나가지 않고, 나중에 볼륨만 다시 붙이면 IP, 보안 그룹, IAM 역할 같은 설정이 그대로 살아나기 때문이다.

##### 스냅샷을 남기고 볼륨 지우기

정리 대상은 6개월 이상 중지된 6대와 1~4개월 중지된 7대, 서버 13대에 붙은 볼륨 19개(4,586GiB)였다. 먼저 13대가 모두 아직 중지 상태인지 확인하고 볼륨 목록을 파일로 고정했다. 이후 모든 단계는 이 목록 기준으로 진행해서 작업 중에 대상이 바뀌지 않게 했다.

그다음 볼륨마다 스냅샷을 만들면서 원래 인스턴스, 볼륨, 장치명, 타입, AZ와 삭제 예정일을 스냅샷 태그로 남겼다. 나중에 사람의 기억이나 작업 파일이 사라져도 태그만 보면 원래대로 복원할 수 있게 하려는 것이었다. 스냅샷이 모두 완료되면 삭제 전에 한 번 더 점검했다. 대상 볼륨과 스냅샷이 19개씩 짝이 맞는지, 그 사이 누가 서버를 켜지는 않았는지 확인했다.

점검이 끝난 뒤에야 볼륨을 서버에서 분리했고, 분리한 볼륨 중에서 그 볼륨으로 만든 완료된 스냅샷이 있는 것만 삭제했다. 19개 모두 삭제했고 건너뛴 건 없었다. 마지막으로 스냅샷 19개가 남아 있고 볼륨이 36개에서 17개로 줄었는지 확인했다. 남은 17개는 실행 중인 서버, 유지하기로 한 4대, 미연결 2개의 볼륨이다.

핵심 명령만 옮기면 이렇다.

```bash
# 1. 스냅샷 생성 (복원 정보는 태그로 남김)
aws ec2 create-snapshot --volume-id $VOL \
  --tag-specifications "ResourceType=snapshot,Tags=[{Key=Purpose,Value=cleanup-backup},{Key=SourceInstance,Value=$IID},{Key=SourceVolume,Value=$VOL},{Key=SourceDevice,Value=$DEV},{Key=SourceType,Value=$TYPE},{Key=SourceAZ,Value=$AZ},{Key=DeleteAfter,Value=2026-11-30}]"

# 2. 서버에서 분리
aws ec2 detach-volume --instance-id $IID --volume-id $VOL

# 3. 이 볼륨으로 만든 완료된 스냅샷이 있을 때만 삭제
OK=$(aws ec2 describe-snapshots --snapshot-ids $SNAP \
  --query 'Snapshots[?VolumeId==`'$VOL'` && State==`completed`] | length(@)' --output text)
[ "$OK" = "1" ] && aws ec2 delete-volume --volume-id $VOL
```

##### 월 $438의 변화

서버 13대에 붙어 있던 볼륨 19개(4,586GiB)를 정리했다. 서울 리전 정가로 계산하면 이 볼륨들이 쓰던 비용은 월 약 $438(약 61만원)이었고, 서비스에 영향을 주는 서버는 하나도 없었다.

|항목|값|
|---|---|
|정리한 서버 / 볼륨|13대 / 19개 (4,586GiB)|
|제거된 EBS 비용|월 약 $438 (약 61만원)|
|관찰 기간 스냅샷 비용|최대 월 약 $92|
|스냅샷 삭제 후 절감|월 약 $438, 연 약 $5,300 (약 730만원)|
|서비스 영향|없음|

환율은 1,400원/$로 계산했다. 스냅샷은 11월 30일까지 관찰한 뒤 삭제할 예정이라, 그때까지는 스냅샷 비용이 일부 남는다. 다만 스냅샷은 실제로 쓴 블록만 저장하므로 위 금액은 상한에 가깝다.

##### 마무리

11월 30일에 이상이 없으면 스냅샷 19개와 껍데기로 남겨둔 서버 13대를 정리할 예정이다.

사실 이번 정리에 어려운 기술은 필요하지 않았다. 꺼진 서버에도 디스크 요금이 나간다는 걸 알았고, 오래 꺼져 있던 서버부터 하나씩 확인해서 지워도 되는 것과 아닌 것을 나눴을 뿐이다. 확신이 없는 부분은 스냅샷으로 되돌릴 길을 남겨두는 것으로 메웠다. 처음엔 아무도 손대지 못하던 25개의 알림이었지만, 확인하는 순서와 되돌릴 방법만 정해두니 생각보다 어렵지 않게 정리할 수 있었다. 다음에 비슷한 알림을 받으면 같은 순서로 확인할 생각이다.
