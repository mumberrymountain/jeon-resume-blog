한 고객사의 보안 팀이 회사 제품을 검토하면서 한 가지 요청 사항을 보내왔다. 제품 내부에서 외부 라이브러리 사용시, 신뢰성에 관한 검증 여부가 포함되어 있는지 확인해달라는 요청이었다. 확인해보니 우리의 빌드 파이프라인에는 외부 라이브러리를 검증하는 단계가 별도로 없었다. 마침 다른 고객사에서도 몇 가지 라이브러리에 관한 보안취약점 검토 요청이 있었는데, 이 기회에 솔루션의 보안취약점을 전체적으로 검토하고 강화할겸 빌드 파이프라인에 보안 스캔 단계를 도입하기로 했다.

일단 보안 스캔 도구로 Trivy를 택했는데, 오픈소스라 별도 비용 없이 바로 쓸 수 있고, 컨테이너로 실행할 수 있어서 Jenkins 에이전트에 따로 설치하지 않고도 붙이기 쉬웠다. 이미 빌드된 이미지 안의 라이브러리와 OS 패키지 취약점을 한 번에 점검할 수 있다는 점도 컸다. 무엇보다 결과를 JSON으로 뽑을 수 있어서, 이를 가공해 레포트로 만들어 고객에게 검증 기록을 보여 줘야 하는 우리 상황에 잘 맞았다.

더불어 개인적으로 빌드시 보안 스캔으로 실패하는 상황은 없어야 한다고 판단했다. 서비스에 포함된 모든 CVE 취약점을 완전히 걷어내는 것은 사실상 불가능하다고 생각했기 때문이다. 설사 취약점을 전부 걷어낸다 해도 매주 새로 공개되는 취약점에 맞춰 그때그때 업데이트하며 빌드가 깨지지 않게 유지하려면 상당한 공수가 들고 개발 속도도 떨어진다. 그래서 스캔은 매 빌드마다 수행하되 빌드는 막지 않기로 했다. 다만 결과를 기록으로 남겨 어떤 취약점이 있는지 추적하고, 우선순위에 따라 대응하도록 설계하기로 했다.

**구성: 빌드 스캔과 주간 스캔**

일단 보안 스캔은 두 군데 두기로 했다. 하나는 기존 빌드 파이프라인 내부의 스캔 스테이지다. 이 스캔 스테이지는 개별 서비스의 보안취약점만을 검증하는 스테이지이다. 다른 하나는 매주 월요일마다 한 번씩 도는 전체 서비스 스캔 Job이다. 이 Job은 모든 서비스를 한꺼번에 스캔해 메일로 두 가지 레포트를 보낸다. HTML 레포트는 서비스별 취약점을 심각도 순으로 정리해 메일에서 바로 읽을 수 있게 만든 문서이며, CSV는 같은 결과를 엑셀 같은 도구에서 정렬하고 필터링할 수 있도록 표 형태로 뽑은 파일이다.

```groovy
stage('Security Scan') { 
   steps { 
      script { 
         load('k3s/jenkins/lib/security-scan-stage.groovy').scan() 
      } 
   } 
}
```

빌드 스캔 스테이지의 본문은 `build.groovy`와 `build-jdk.groovy`가 함께 쓰는 공용 파일 하나로 모아 두고, 각 파이프라인에서는 그 파일을 불러와 호출만 하도록 처리했다. 두 파이프라인이 같은 스캔 스테이지를 쓰는 구조라서, 스테이지를 각각 복사해 두면 한쪽만 고치고 다른 쪽을 빠뜨리기 쉽다. 한 곳에서 관리하면 수정이 한 번으로 끝나 유지보수 측면에서 낫다고 판단했다.

이 스테이지는 ‘Push to Registry’ 다음, ‘Cleanup’ 앞에 두었다. Cleanup이 `docker rmi`로 로컬 이미지를 지우기 때문에, 이미지가 로컬에 남아 있는 마지막 구간이 여기이기 때문이다. 

```bash
timeout --kill-after=30s 15m docker run --rm \
    -v /var/run/docker.sock:/var/run/docker.sock \
    -v trivy-cache:/root/.cache/trivy \
    aquasec/trivy image \
        --scanners vuln,license \
        --format json \
        --exit-code 0 \
        '<이미지>' \
    > result.json 2> scanner.log
```

Trivy는 Jenkins 에이전트에 설치하지 않고, 호스트의 docker 소켓을 마운트한 컨테이너로 실행한다. 빌드된 이미지가 이미 호스트 docker에 있어서 따로 내보낼 필요가 없고, 취약점 DB는 named volume에 캐시해 두어 매 빌드마다 약 50MB를 다시 받지 않는다. 결과는 JSON 파일로 받아 집계하고, 로그에는 HIGH/CRITICAL 상위 몇 건만 출력하며 전체 결과는 `security-reports/`에 아카이브한다.

주간 스캔은 빌드와 무관하게 월요일마다 도는 별도 Job이라, 스캔할 이미지를 레지스트리에서 직접 pull해서 서비스를 하나씩 순서대로 스캔한다. 결과는 서비스별로 집계해 HTML 레포트와 CSV로 만들어 메일로 보낸다. 처음에는 레포트에 CVE 건수를 그대로 집계해서 보여 줬는데, 메일을 받아 본 쪽에서 숫자가 지나치게 커 보인다는 지적이 나왔다. 하나의 패키지만 업그레이드해도 한꺼번에 해결될 취약점들이 각각 별개의 건으로 중복 집계되고 있었기 때문이다. 그래서 조치 대상(CRITICAL, HIGH)을 CVE 단위가 아니라 패키지 단위로 묶고, 패키지마다 현재 버전과 올려야 할 권장 버전, 검출 건수를 한 줄로 보여 주도록 바꿔서, 어떤 패키지를 어느 버전으로 올리면 몇 건이 한꺼번에 해결되는지 바로 알 수 있게 했다.

**실패하지 않는 스테이지 만들기**

막상 해 보니 진짜 일은 Trivy를 붙이는 것이 아니라, 어떤 경우에도 빌드를 실패시키지 않는 스테이지를 제대로 만드는 것이었다. 이를 코드로 보장하기 위해 스테이지의 모든 로직을 `try/catch`로 감쌌고, `sh`는 전부 `returnStatus`로만 받게 했다. 설정 파일이나 공용 로직 파일이 없을 때도 에러를 내지 않고 "건너뜀" 로그만 남기고 지나간다. 그런데 이렇게 만든 스테이지에서 의도와 다르게 동작하는 부분이 몇 가지 나왔다.

```groovy
try {
    // 스캔 로직 전체
} catch (InterruptedException e) {
    // 사용자 Abort — 삼키지 않고 다시 던진다
    throw e
} catch (Exception e) {
    echo "[SCAN] ⚠️ 스캔 처리 중 오류 — 빌드에는 영향 없음"
}
```

일단 사용자의 Abort까지 삼킨다는 문제가 있었다. 빌드는 실패하지 않아야 하는지라 `catch (Exception)`로 로직을 감쌌는데, Jenkins에서 빌드를 Abort하면 발생하는 `FlowInterruptedException`이 `InterruptedException`을 상속하기 때문에 해당 catch가 사용자의 중단까지 삼켜버렸다. 스캔 중에 중단을 눌러도 "스캔 처리 중 오류 — 빌드에는 영향 없음"이 찍히고 조용히 다음 단계로 넘어갔다. 더 큰 문제로 Jenkins의 `timeout` 스텝도 만료되면 똑같이 `FlowInterruptedException`을 던져버렸다. 이러면 타임아웃과 사용자 Abort가 같은 예외로 들어와서 둘을 구분할 방법이 없다. 

그래서 Jenkins `timeout` 스텝은 쓰지 않고 셸의 `timeout` 명령으로 시간 제한을 걸었다. 이렇게 하면 타임아웃은 종료 코드(124 또는 137)로 돌아오고, `InterruptedException`이 들어오면 그건 곧 사용자의 Abort라고 확신할 수 있다. 이후 `catch (Exception)`보다 앞에 `InterruptedException`을 먼저 잡아 그대로 다시 던지도록 해서, 사용자의 중단은 삼키지 않게 했다. "어떤 경우에도 빌드를 실패시키지 않는다"는 원칙에 예외가 하나 생긴 셈이지만, 사용자가 명시적으로 중단하는 것까지 막아서는 안 된다고 판단했다.

다음 문제는 `docker pull`의 종료 코드가 항상 0이었다는 것이다. 로그를 줄이려고 `docker pull ... | tail -5`처럼 `tail`을 붙였는데, 파이프로 이은 명령의 종료 코드는 마지막 명령인 `tail`의 것이라서 pull이 실패해도 0이 나왔다. Jenkins `sh`가 쓰는 dash에는 `pipefail`도 없어서, `returnStatus`로 받아도 pull이 성공했는지 알 방법이 없었다. 그래서 pull 출력은 변수에 담아 두고 종료 코드를 따로 보존한 뒤 마지막에 그 값으로 종료하는 `pullCommand()`를 만들어, pull은 전부 이 함수로 통일했다.

더불어 다른 문제로, Rust 서비스가 스캔 결과에 아예 잡히지 않았다는 문제가 있었다. Rust 바이너리 컴파일시 의존성 정보가 사라져 버리기 때문이었다. Rust는 의존하는 크레이트들을 컴파일 과정에서 하나의 실행 파일로 합쳐 버리고, 어떤 크레이트의 몇 버전이 들어갔는지는 바이너리에 기록하지 않기 때문에, 이미지에 남은 실행 파일만으로는 Trivy가 읽어 낼 의존성 목록이 없다. 

```dockerfile
RUN cargo install cargo-auditable --version 0.7.5 --locked 
# 일반 cargo build 대신 cargo auditable build 를 쓴다 
RUN cargo auditable build --release --locked
```

해결책은 `cargo-auditable`로 빌드하는 것이었다. `cargo auditable build --release`로 빌드하면 바이너리의 `.dep-v0` 섹션에 의존성 목록이 함께 심어지고, Trivy가 이 정보를 읽어 크레이트의 취약점을 잡아낸다. 다만 `--locked`는 `cargo-auditable`이 쓰는 의존성만 `Cargo.lock`대로 고정할 뿐 도구 자체의 버전은 고정하지 않기 때문에, 설치할 때 `--version 0.7.5`를 명시해 버전을 고정했다.

타임아웃은 단계별로 따로 걸면 합산된다는 점도 뒤늦게 알았다. pull과 scan에 각각 15분씩 제한을 걸었더니, 두 단계가 별개의 시간 예산이라 최악의 경우 이미지 하나에 30분이 걸릴 수 있었다. 그래서 `pullTimeoutMinutes: 5`를 따로 두어, 이미지 하나의 최악 시간을 약 21분(pull 5분 + scan 15분 + 강제 종료 대기 30초씩 두 번)으로 줄였다.

마지막으로, 긴급하게 패치한 문제도 있었다. 주간 스캔 Job이 도는 Jenkins 폴더 이름이 `test Dev`처럼 공백과 괄호를 포함하고 있었다. 여러 Job이 동시에 `docker login`을 하면 서로의 인증 정보를 덮어쓰는 문제를 피하려고 `DOCKER_CONFIG`를 Job별 경로로 분리하고 있었는데, 이 경로를 따옴표 없이 `mkdir -p`에 넘기는 바람에 `Syntax error: "(" unexpected` 에러가 났다. 셸에서 `(`는 서브셸 문법이라서 경로가 그대로 해석된 것이다. 경로를 작은따옴표로 감싸서 해결했다.

**메일 발송과 운영 설정**

레포트를 메일로 보내면서 수신자와 발신 계정은 코드에 두지 않기로 했다. 수신자와 발신자는 Jenkins Credentials(Secret text)에 두고, 설정 파일인 `security.yaml`에는 그 Credential의 ID만 적었다. 수신자는 쉼표, 세미콜론, 공백, 줄바꿈 아무거나로 여러 명을 나열할 수 있고, Credential이 없으면 메일만 생략되고 레포트 아카이브는 정상적으로 동작한다.

SMTP 계정은 JCasC로 넣지 않고 Jenkins UI에서 직접 입력했다. K8s Secret은 base64로 인코딩되어 있을 뿐이라 `kubectl get secret -o yaml`로 누구나 복호화할 수 있는 반면, Jenkins Credentials 저장소는 자체 키로 암호화한다. 반면 메일 발송에 필요한 플러그인(`email-ext`, `htmlpublisher`)은 `values-override.yaml`의 `installPlugins`로 git에서 관리하도록 세팅했다. `plugin-dir`이 emptyDir이라 파드가 재기동되면 이 목록을 기준으로 초기화되기 때문이다.

**배운 점**

이번 작업에서 가장 크게 배운 건, "실패하지 않는" 스테이지는 모든 예외를 삼키는 스테이지가 아니라는 점이다. `catch (Exception)`은 사용자의 Abort까지 삼키고, 파이프로 이은 명령은 앞 명령의 실패를 가리며, 단계별로 따로 건 타임아웃은 합산된다. 무엇을 삼키고 무엇을 전파할지, 실패를 어떻게 감지할지를 하나하나 따져야 했다. 또 스캔 결과가 0건이라면 안전한 것이 아니라 스캔이 안 된 것일 수 있다는 점을 Rust 서비스에서 확인했다. Trivy를 붙이는 일 자체는 어렵지 않았지만, 빌드는 막지 않으면서도 믿을 수 있는 기록을 남기는 일에는 이런 세부 사항이 필요했다.
